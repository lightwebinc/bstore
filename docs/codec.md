# The codec

bstore's byte-level contract is implemented twice, once in Go and once in
TypeScript, and both are held to one set of golden vectors that the Go codec
generates. This page says where each piece lives, how the two are kept equal,
and the readings the codec takes where [spec.md](spec.md) leaves a case open.

## Layout

| Path | What it is |
| --- | --- |
| `internal/storerec` | The Go codec: the records, hold terms, the key map, its fold and contexts, the page checks, the proof tree, challenges, settlement, BRC-26 advertisements, the classifier, the topic manager's transaction rules, lookup questions, a reader's checks and the closure checks |
| `internal/vectors`, `cmd/vectors` | The vector generator; every check it makes fails the run when it stops holding |
| `testdata/vectors` | The golden vectors (spec section 22), JSON |
| `host/src` | The TypeScript twin, read against every vector |
| `host/vendor` | The bcommon TypeScript package at the tag go.mod pins, packed from that tag |

What the codec takes from elsewhere:

- bcommon: `cbor`, `record`, `guard`, `pushdrop`, `carrier`, `chaintoken`,
  `commit` (RFC 6962 roots and compact paths over leaves of any length),
  `chirp` (CHIRP Profile 1: node encoding, the canonical construction, the
  closure check, identifiers) and, for the vectors, `mint`; in TypeScript the
  same readers and checks.
- go-sdk v1.5.2 and `@bsv/sdk` 2.7.1, the versions bcommon pins. The SDK
  release bcommon pins does not carry the SDK's advertisement check
  (`storage/UHRPAdvertisementValidation.ts`), so both codecs carry it step
  for step (`advert.go`, `advert.ts`).

## Building and checking

```sh
cd host && npm ci && cd ..
make verify NODE=/path/to/node24
```

`make verify` runs gofmt, vet, the dependency check, the TypeScript type
check, the vector check (the generator run in memory and compared byte for
byte with the files) and both test suites, the page checks against their
oracle included. `make vectors` rewrites the vectors; a change to them is a
change to the contract's goldens. `make fuzz` runs each decoder and the
advertisement check under the Go fuzzer.

## How the two codecs are kept equal

- Every record vector decodes in TypeScript to the Go codec's view and
  re-encodes to the Go bytes; every refusal vector is refused for the same
  label and, where a label covers several rules, the same rule.
- Every map root, fold, batch, object answer, context, page and abstract
  page reaches the Go codec's value or verdict; so do a reader's walks and
  head checks.
- Every proof root (to 257 blobs), path, index, response through the
  buyer's check with a fetcher's faults, and answerer's refusal reaches the
  Go codec's verdict; the detection tables are generated by both.
- Every payout, derivation and settlement, question, closure and
  transaction reaches the Go codec's value or verdict.
- The page checks are also run against an oracle: a port of the contract
  review's brute force, over every map of one to six keys of up to three
  letters, every prefix, cursor, start, page and role combination (about 38
  million pages). The checks agree with the oracle on every page, accept no
  page it calls unsound and refuse no honest page. A sample of those pages is
  in `map-v1.json` for the TypeScript twin.

## Readings the codec takes

These are readings of the spec, pinned by the vectors. Rows C1 to C5 of
frozen.md section 14 are clarifications pending the owner's confirmation;
everything below is the codec's.

**Types and rules.** A fixed-length byte string of another length is
`type` (the table's type is `bytes(32)`); an identity key that is a byte
string but breaks the key rule, or is the anyone key, is `identity`; a value
of another CBOR type is `type`. A key's own label is used only for a value of
the right type. A negative integer where an unsigned one is wanted is
`type`. More than 64 keys is `too-large` (bcommon `record`). Every unsigned
value the spec leaves unbounded is at most 2^53 - 1.

**The bucket record's lists.** `writers`: more than 16 is `writers`; then
each element must be a key (`identity`, a non-byte element included); then
strictly ascending and none the owner (`writers`). `changes` and `consumed`:
every failure inside the list is the key's own label, the list's type
`type`. Keys in `changes` are ascending by their UTF-8 bytes, as everywhere.

**The entry.** A put's keys 7 to 15 are read where present, in key order,
then `kind` checks presence; a delete's keys 7 to 15 are not read, and any of
them present is `kind`; a kind from 3 to 255 keeps its keys 7 to 15 as read,
unchecked. `contentType` is read literally: 3 to 127 bytes of 0x21 to 0x7e,
no capital letter, exactly one `/`, no `;`; an empty type or subtype is not
refused. `etag`'s printable ASCII is 0x20 to 0x7e. Any failure inside `hold`
or `meta` is `hold` or `meta`; the value of another type is `type`.

**The piece.** Spec section 5 lists no refusal order; the piece follows the
others: the record steps, then `bucket`, `identity` (writer), `type` (root),
`piece` (1 to 4,194,304 bytes).

**The front statement's url.** Besides the listed rules, the authority (up
to the first `/` after `https://`) is not empty.

**The request.** Every refusal is `request`, and the rule names the step:
the record steps, `unknown-key` (a key above 10) right after the magic, then
per key `missing`, `type` and `identity`, `size`, `seed-height` (`seedHeight`
at most 2^32 - 1), `c`, `range`. The response body read at the buyer's step 2
names its rule `body-` and the step, then `request-hash`, `answerer`,
`inline-from-front`; step 3 names `samples` or `path-length`; step 1
`shape` or `verify`. A signed response over 8,388,608 bytes is `signature`
(`shape`).

**The buyer's check.** A by-reference sample whose fetch fails, or whose
fetched segment fails steps 5 or 6, is rechecked from the whole blob,
held to its CHIRP blob hash: the verdict names the step that first failed
(`fetch`, `segment` or `path`) with the outcome `unretrievable` when the blob
fails or cannot be fetched, or `invalid` with the step that fails on the
blob's segment; a sample that passes on the blob is listed as rechecked and
the response may still pass.

**Contexts.** An entry context is refused (`map`) as `too-large` over 1,024
bytes, `cbor`, or `shape`: anything but `[index, path]`, an index of 1,048,576
or more, more than 20 steps, a step not 32 bytes. A token context the same
over 4,096 bytes, and `shape` for more than two leaves, a leaf not `[role,
index, key, C, path]` of its types, a role above 2, a key that is not an
object key, roles not ascending, or role 1 beside role 2. A reader decodes a
context before it checks it. The well-formed contexts never reach their byte
bounds (an entry's at most about 690 bytes, a token's about 3,500).

**Page and object checks.** Every path is checked first (`path`), then
checks 1 to 4 of spec section 11.3 in order (`check-1` to `check-4`), all
under the label `map`. An object answer is `object-shape` (an entry with a
token context, or without its own), `object-unheld` (a role 2 leaf for
another key) or `object-absence`.

**The fold.** A token that names a commitment named before, in the chain or
earlier in its own changes and consumed, is `map-mismatch` (reason
`named-twice`) before its change is applied; so a put of the value a key
already names, whose commitment the chain has named, is reported
`named-twice`. The other reasons are `removal-of-absent`, `count`,
`too-many-keys` and `map-root`.

**The owner's batch.** Kinds other than put and delete are never applied;
an entry named twice in one batch counts once.

**Advertisements.** The check follows the SDK's in its order and names the
rule that failed: `pushdrop`, `field-size`, `host`, `hash`, `url`, `expiry`,
`file-size`, `signature`, `lock`, `verify`, all under the label
`advertisement`. The url is parsed as the WHATWG URL parser parses it. The
Go codec does that for every url whose host is ASCII after percent-decoding
and has no label beginning `xn--`; an internationalised host, which the
WHATWG parser maps through UTS #46, the Go codec refuses (rule `url`) and the
TypeScript twin, which runs the WHATWG parser itself, decides. The narrowing
only ever refuses: the Go codec never admits an advertisement the SDK
refuses. Hosts are the TypeScript twin's.

**Transactions.** An output of more than 2^53 - 1 satoshis anywhere in the
BEEF is refused as `beef` before any rule, as bchat does. A transaction that
claims nothing and holds an advertisement or a hold-shaped output is a mined
object, whatever its output 0; otherwise a sweep needs one or two outputs.

**Settlement.** Ties in first sight go to the lower advertisement txid in
display order, as the contract orders txids in answers.

**Reader labels for a closure.** Step 6 `root` covers the root's rules and
every refusal of the closure that the bytes cannot mend (a node's checks, a
length, the depth, a cycle, the references bound, the 2^43 bound, the
construction); step 7 `closure` covers objects not served as their hashes
name them; step 8 `content` the content hash; step 9 `proof-root`.

**Questions.** A refused question is the label `query`. Each value is
checked as a JSON parser that decodes to UTF-8 holds it, a lone surrogate
read as U+FFFD. The member `outcome-history-of` is a provider's key, held to
the key rule like `outcome-history`.
