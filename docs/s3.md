# The S3 gateway

`bstore s3d` is a reader and a writer for clients that speak S3
([spec.md](spec.md) section 16). A read is proven against the bucket's
chain: the latest token, the map's proof of what a key names (or that it is
absent, or that a listing page is complete), the entry, and every byte of
the object held to its hash before it is sent. A write builds the object's
CHIRP closure and proof root while the body streams, mints a hold output
when the gateway asks for a bounty, and publishes the pieces and the entry
over the plane or by unicast. This page is in four parts: the model, the
compatibility matrix, the limits, and an operator's guide.

## The model

### Buckets

An S3 bucket name is the bucket identifier with every `_` replaced by `-`
(`example_photos_hmqzvtkwrx` is `example-photos-hmqzvtkwrx`). The gateway
serves the chains its configuration names, each by its identifier, owner
and bucket id; `ListBuckets` answers those. An identifier whose S3 name
would begin `sthree-` is refused at start.

### Authentication: gateway mode

Requests are signed with AWS Signature Version 4 (`AWS4-HMAC-SHA256`), in
the `Authorization` header or as a presigned URL. There is no anonymous
access and no Signature Version 2.

- **Access keys map to identities.** Each access key the operator
  configures names one identity: a writer key whose wallet lives under the
  gateway's data directory. Every write made with that access key is
  signed and paid for by that identity. Several access keys may share one
  identity; an access key may be limited to some buckets.
- **The owner decides what is anchored.** An identity's entries become
  part of a bucket when the bucket's owner anchors them, which the owner
  does for its own key and the writers its latest token names. The owner
  adds the gateway's identity to `writers` (spec section 3.5); entries by
  an identity the owner does not name are never anchored, and other
  readers never see them.
- **Secrets are the operator's.** Each access key has its own secret (16
  to 256 characters), inline in the configuration or in a file. The
  secret never leaves the gateway; the identity's private key never
  leaves its wallet.
- **What a signature binds.** The signed headers must include `host`
  and every `x-amz-*` header and `Content-MD5` the request carries, so
  nothing that changes what is written rides unsigned. The request time is
  held within 15 minutes of the gateway's clock; a presigned URL lives at
  most seven days. The credential scope must name the gateway's region
  and the service `s3`.
- **Replay.** A publishing write (`PutObject`, `CopyObject`,
  `CompleteMultipartUpload`, `DeleteObject`, `DeleteObjects`) whose
  signature the gateway has seen and answered successfully, within the
  signature's life, is answered again with the first answer: its body is
  not read and nothing is published twice. One still in progress is
  answered `409 OperationAborted`. A write that failed is not remembered,
  so a client's retry runs. Each access key holds at most
  `limits.replay_per_key` signatures (a presigned URL's for its whole life);
  past it, that key's publishing writes answer `503 SlowDown` until some
  expire, and no other key is affected. `UploadPart` and
  `CreateMultipartUpload` publish nothing and are not cached: a part sent
  again rewrites itself, and a completion names every part's MD5, so a part
  a replay swapped is refused there.

A wallet-signed native mode is not in this version.

### Writes

- **PutObject** stages the body into the local store as it streams (one
  4 MiB blob and one segment in memory), checks every digest the request
  declares, and only then publishes: a hold output when a bounty is
  configured, then one piece per distinct object of the closure on the
  bucket's blob topic, then the put entry on the records topic. The answer
  is `200` once the entry is sent: the facade took it, or, without a
  facade, a quorum of the hosts (a target that refuses it does not count).
  A `200` does not mean held: no provider may have advertised yet.
- **Hold outputs are minted ahead**, `hold_tree` to a transaction (16 by
  default, up to 1,024: a hold output is named by the entry and carried in
  no BEEF, so a tree of them costs no carrier anything), so that
  each identity keeps `hold_ahead` mined hold outputs of the configured
  bounty ready and a put never waits for a block (a writer SHOULD mine its
  hold output well before the entry, spec section 9.4). A put that finds
  none ready waits up to 30 seconds, then answers `503 SlowDown`. Each is
  marked taken, and saved, before its entry is signed, and goes to the
  bucket's records topic with the entry. The pool refills by as many
  transactions a block as it has coins for (a transaction minted while more
  are owed leaves its change in a coin for each of them), so `hold_ahead`
  is a depth: size it to the puts one block interval must absorb, and the
  sustained rate is that many per block.
- **Funding trees are minted ahead too.** Each piece carrier spends one
  output of a mined funding tree, and each entry one output of an entry
  tree. Trees are minted, and mined, in the background whenever a put
  leaves `piece_ahead` (or `entry_ahead`) outputs or fewer ready across the
  current tree, the trees held for a switch and the trees being minted: as
  many trees as it takes, up to eight a put and as many as the pool has
  coins for. A put spends what the current tree has left before it
  switches. By default `piece_tree` is the pieces of the largest
  `PutObject` (`limits.max_object`), at most 1,023, and `piece_ahead` is one
  tree, so a put never waits for a block; a larger one spans trees and
  waits for each beyond the ones ready. Entry trees default to 16 outputs
  with half a tree ahead, which holds a writer to 16 puts a block interval:
  set `entry_ahead` to the puts one block interval must absorb (600, say)
  and the gateway keeps that many entry outputs ready across as many small
  trees as it takes, each entry carrier carrying only its own small tree.
  Trees an earlier run minted ahead and did not use are held again at the
  next start and used before more are minted.
- **Pieces go `piece_workers` at a time** (default 4): each minted, synced
  to the outbox and sent to every target, and the next started as soon as
  a worker is free. A piece no target took stops the put; those in flight
  finish.
- **The race runs in the background.** For each identity's own puts with a
  bounty the gateway judges the race (spec section 9.4), settles it by
  rank once it closes, sends the remittances until they are taken, and
  reclaims the hold output after the deadline when nothing settled: what
  `bstore holds`, `settle` and `reclaim` do by hand ([usage.md](usage.md)).
  `race.off` leaves it to those commands, run with `-home` at the
  identity's directory while the gateway is stopped.
- **An entry made but not taken.** When the facade or the host quorum does
  not take an entry, the gateway asks again for about 15 seconds, then
  answers `503 SlowDown`; the entry stays in the outbox and is delivered.
  The same write sent again within an hour (same identity, key, content,
  content type, ETag and metadata), while that entry is still the key's
  newest pending one and was answered `503`, is answered `200` from it and
  makes no second entry;
  a retry after another write to the key makes a new one, and the later
  decides the key. The same write or copy sent again while the first is
  still publishing (a client that timed out waiting and resent) waits for
  that publish and answers as it does, with no second entry or race. A completion whose entry was made is
  remembered: sent again, it answers the same and publishes nothing.
- **Multipart uploads** are the gateway's own state. Parts are kept on
  disk as they arrive, cut into 4 MiB blobs and hashed as they stream in,
  and the whole object's SHA-256 is taken over the parts as they become
  contiguous; a part is acknowledged once it and its record are synced.
  Completion assembles the parts in the order named and publishes one
  entry. When every part but the last is a whole number of 4 MiB blobs
  (8 MiB and 16 MiB parts, the AWS CLI's, boto3's and mc's defaults, are),
  the parts' blobs are the object's blobs: they are linked into the local
  store and the closure is built from their recorded hashes, without
  reading the content again. Other part sizes are read back and re-chunked
  at completion. Either way the closure is the one a `PutObject` of the
  same bytes builds. Every part and the completion go to the gateway that
  began the upload, with the access key that began it.
- **CopyObject** is a new put entry naming the source's root, size,
  content hash and proof root. Within one bucket nothing is published
  again. Across buckets the closure is published on the destination's blob
  topic, from the gateway's local copy or read from the source's
  advertisers, every object held to its hash.
- **DeleteObject** is a delete entry; `204`. The key leaves the map at the
  owner's next token.
- **Save before send.** The funding outputs a write spends are recorded
  used before any carrier is signed, every carrier is written to the
  identity's outbox before it is sent, and whatever a target did not take
  is sent again, the same bytes, by the background run and after a
  restart, for up to a week. A piece carrier is kept by reference to the
  local store's copy of its object (the object is pinned there while it is
  owed), and a put's pieces share one batch file whose writes are synced
  together. Funding trees are recorded with their fee coin before they
  reach the settlement leg and settled on the next start.
- **Small coins are merged.** Change, refunds of lapsed bounties and
  payments each arrive as a coin of their own, and the identity's pool is
  one file rewritten whole on every change. Once more than 64 coins of
  under 1,000,000 satoshis are spendable, the background run merges up to
  250 of them, smallest first, into one coin a minute, spendable once the
  merge mines. A coin that small funds no hold transaction.

### Reads

- **The chain.** A gateway new to a chain walks it back to its first token
  (spec section 15.1), one host question per token, in the background:
  reads wait for it while their own request lasts, then answer `503`, and
  the walk goes on. Afterwards only new tokens are walked. The walk is not
  kept across a restart. Every token walked drops the gateway's pending
  entries it names.
- **HeadObject** proves the key (spec section 15.2 steps 1 to 5) and never
  asks a provider.
- **GetObject** opens the closure (the root and every branch, each held to
  its hash, the root to bstore's root rules, the tree to Profile 1's
  canonical construction) and then reads only the blobs the range
  overlaps, each whole and held to its hash before a byte of it is sent.
  A whole read also holds the content to `contentHash` before the last
  blob is sent, so a whole object whose content hash fails is never
  released complete. Bytes come from the gateway's local store first, then
  from the advertisers the hosts answer: verified advertisements, unexpired,
  latest expiry first. An advertiser that serves other bytes, fails, or
  does not answer is named in the log, skipped, and asked last for ten
  minutes; at most eight are asked for one object, each for at most a
  minute (15 seconds to begin answering).
- **ListObjectsV2** walks `list` pages, each proven complete against the
  latest token (spec section 11.3). A key a page names as unheld is read
  by `entry` at another host, and the listing answers `503` if no host
  produces it. The delimiter is applied by the gateway to the proven keys.
- **Read your writes** at the writing gateway: its own pending entries
  answer at once, a newer pending put or delete over an anchored entry,
  in heads, gets and listings alike. Other gateways see a write once a
  token anchors it. Pending entries are kept until an anchored entry for
  the key is the same or newer, for at most a week, and the newest 10,000.
- **Not found.** `NoSuchKey` only on a proven absence, or at the writing
  gateway when its own pending delete is newer than the anchored entry.
  `503 SlowDown` when no host answers anything that verifies, or when the
  map names a key's entry and no host produces it. A host whose answer
  does not verify is named in the log and the next host is asked. A token
  below the one the gateway already verified (a rollback, or a host that
  is behind) is not used; neither is a token the chain view shows spent.

## Compatibility

### Operations

| Operation | Supported | Notes |
| --- | --- | --- |
| `ListBuckets` | yes | the configured buckets the access key may use |
| `HeadBucket`, `GetBucketLocation` | yes | the configured region |
| `ListObjectsV2` | yes | `prefix`, `delimiter`, `max-keys` (at most 1000), `start-after`, `continuation-token`, `encoding-type=url` |
| `ListObjects` (version 1) | yes | `marker` and `NextMarker` |
| `HeadObject`, `GetObject` | yes | one byte range; `If-Match`, `If-None-Match`, `If-Modified-Since`, `If-Unmodified-Since`; the `response-*` overrides; presigned URLs |
| `PutObject` | yes | `Content-MD5`; flexible checksums; user metadata; `Content-Type` |
| `CopyObject` | yes | `COPY` and `REPLACE` metadata directives; within and across buckets |
| `DeleteObject`, `DeleteObjects` | yes | up to 1000 keys a request |
| `CreateMultipartUpload`, `UploadPart`, `CompleteMultipartUpload`, `AbortMultipartUpload` | yes | one gateway per upload |
| `ListParts`, `ListMultipartUploads`, `UploadPartCopy` | no | `NotImplemented` |
| Conditional writes (`If-Match`, `If-None-Match` on a put, a completion or a delete) | no | `501 NotImplemented`, never ignored: a client that relies on them for locking must not believe it holds a lock |
| Conditional copies (`x-amz-copy-source-if-*`) | no | `NotImplemented` |
| Versioning, ACLs other than `private`, policies, lifecycle, tagging, object lock, encryption headers, storage classes other than `STANDARD`, website, CORS, presigned POST, bucket creation and deletion, reading by part number | no | `NotImplemented` |
| Signature Version 2, anonymous requests, session tokens | no | `AccessDenied` or `InvalidArgument` |
| Virtual-host addressing | when `domain` is set | `<bucket>.<domain>`; path style always |

### Request bodies

| Form | Supported |
| --- | --- |
| A plain body with `x-amz-content-sha256` the body's SHA-256 | yes, checked before anything is published (`XAmzContentSHA256Mismatch`) |
| `UNSIGNED-PAYLOAD` | yes |
| `STREAMING-AWS4-HMAC-SHA256-PAYLOAD` (signed chunks) | yes, every chunk signature checked |
| `STREAMING-UNSIGNED-PAYLOAD-TRAILER` (the default of current AWS SDKs over TLS) | yes, the trailing checksum checked |
| `STREAMING-AWS4-HMAC-SHA256-PAYLOAD-TRAILER` | yes, the chunk and trailer signatures checked |
| Flexible checksums `CRC32`, `CRC32C`, `CRC64NVME`, `SHA1`, `SHA256`, in a header or a trailer | yes, checked (`BadDigest`) and echoed |
| A body without `Content-Length` | only aws-chunked, with `x-amz-decoded-content-length` |

### What a client sees

| Header or field | Value |
| --- | --- |
| `ETag` | for `PutObject` the body's MD5; for a multipart upload the MD5 of the parts' MD5s, `-`, the number of parts; an entry without one `"<root hex>-1"`. Informative: integrity is the CHIRP root and the content hash |
| `x-amz-checksum-sha256`, `x-amz-checksum-type` | the base64 of the whole object's SHA-256, `FULL_OBJECT`, on `HeadObject` and a whole `GetObject`, multipart objects included (S3 itself gives those a composite checksum); none on a ranged answer |
| `x-amz-meta-bstore-root` | the CHIRP root, hex. User metadata keys starting `bstore-` are reserved and refused on a put |
| `x-amz-meta-*` | the entry's metadata: keys of `a-z`, `0-9` and `-`, sent in lower case; values on one line |
| `Content-Type` | lowercased without parameters on a put; `application/octet-stream` when absent or not a plain `type/subtype` |
| `Last-Modified` | the entry's `created`, the writer's claim; the anchoring token's block is the proven bound |
| Listing `Owner`, `StorageClass` | no owner; `STANDARD` |
| `CompleteMultipartUpload` | the answer begins at once and is kept alive with whitespace while the gateway publishes; a failure after that is an error document in a `200`, as S3 does. Its `x-amz-checksum-*` headers are the whole object's and are checked against the assembled object (a composite value is not checked) |
| An error after a `GetObject` has begun | the answer ends early; the declared `Content-Length` makes the truncation visible |

### Clients

| Client | Result |
| --- | --- |
| AWS CLI version 2 (botocore inside) | the end-to-end test drives it: `s3api` puts, heads, gets with ranges, copies, deletes, conditional writes, pagination; `s3 cp` multipart; `s3 ls` |
| Terraform S3 backend | writes and reads its state; with `use_lockfile`, its conditional write gets `501 NotImplemented` and Terraform stops with an error rather than believing it holds a lock |
| Other SDKs | the same SigV4 and body forms; the AWS documentation's signing examples are among the unit tests |

## Limits

| What | Default | Key |
| --- | --- | --- |
| A `PutObject` body | 5 GiB | `limits.max_object` |
| A multipart object | 100 GiB | `limits.max_upload` |
| One part; part numbers | 5 GiB; 1 to 10,000 | `limits.max_part`, `limits.max_parts` |
| The smallest part but the last | 5 MiB | S3's rule (`EntityTooSmall`) |
| Uploads open | 1,000, 100 per access key, each for a day | `limits.uploads`, `limits.uploads_per_key`, `limits.upload_seconds` |
| Bodies streaming in at once (puts) | 32 | `limits.stages`; past it `503 SlowDown` |
| Writes publishing at once (puts, copies, completions, deletes) | 8 | `limits.writes`; a put takes its slot only once its body is in |
| Part uploads at once | 32 | `limits.part_writes` |
| Object reads at once | 32 (one 4 MiB blob in memory each) | `limits.reads` |
| Requests of one access key | 200 a second, burst 400 | `limits.requests_per_sec`, `limits.burst` |
| A stalled body or answer | 60 s between reads or writes | `limits.idle_seconds` |
| The slowest body | 16 KiB a second on average, after its first 60 s | `limits.min_rate` |
| Heads, gets and listings asking hosts at once | 64 | `limits.lookups` |
| Request headers | 64 KiB, read within 10 s | |
| A completion, a `DeleteObjects` body | 4 MiB, 2 MiB | |
| Keys in one `DeleteObjects` | 1,000 | `limits.delete_keys` |
| Keys in one listing answer | 1,000 | S3's `MaxKeys` bound |
| Host pages one listing request may walk | 2,000 | |
| A host's answer | 32 MiB | |
| Advertisements asked per root | 256 (four pages) | |
| Pending entries kept for reading the gateway's own writes | 10,000, each at most a week | |
| Signatures remembered against replay | 20,000 per access key | `limits.replay_per_key` |
| The local store | 8 GiB, least recently used closures first; what a cut-short put left, after an hour | `store_bytes` |
| Mined hold outputs kept ready | 8 per identity | `hold_ahead` |
| Piece funding trees kept ready | as many as hold `piece_ahead` outputs across the current tree, the trees held and the trees being minted (one tree by default) | `piece_tree`, `piece_ahead` |
| Undelivered objects | sent again for a week; past 8 GiB owed per identity, puts are refused until a target takes what it owes | `outbox_bytes` |
| Clock skew of a signed request | 15 minutes | |
| A presigned URL | at most seven days | |

Memory is bounded per request: a write holds a few blobs (one per core
hashing them, at most 8, and two more) and streams the rest through the
local store; a read holds one blob; a
listing holds one host page (at most 256 entries) at a time. Disk holds
the local store (bounded, beside the closures being staged), the open
uploads' parts (bounded by the upload limits) and the outbox: each object
until every target took it, for at most a week, and at most
`outbox_bytes` owed per identity before puts are refused.

An identity's puts run side by side, up to the write slots: only the
moment a put takes its funding-tree outputs is one at a time, per tree
kind, so that no two puts spend the same outputs. Writes by several
identities run side by side too.

## Operating

### Configure

A JSON file; an unknown key is refused. No node is needed: with no
`chain`, `settle` or `headers` the gateway reads the chain from
WhatsOnChain (every header held to its proof of work, every proof to those
headers) and broadcasts through GorillaPool's public arcade. A gateway
that writes much exceeds WhatsOnChain's free 3 requests a second: give it
`woc_key` (and `woc_rate`), or a node of its own (`chain`).

```json
{
  "data": "/var/lib/bstore-s3d",
  "listen": "127.0.0.1:9000",
  "region": "us-east-1",
  "mainnet": true,
  "hosts": ["https://overlay.example.com"],
  "facade": "https://plane.example.com",
  "identities": ["main"],
  "access_keys": [{"id": "EXAMPLEACCESSKEY", "secret_file": "/etc/bstore-s3d/main.secret", "identity": "main"}],
  "buckets": [{"bucket": "example_photos_hmqzvtkwrx", "owner": "02...", "id": "..."}],
  "bounty": {"satoshis": 20000, "t": 2, "k": 3, "retention_seconds": 2592000, "deadline_blocks": 144, "check_c": 30}
}
```

| --- | --- | --- |
| `data` | required | the data directory, absolute: `identities/<name>/` (wallet, funding trees, outbox), `store/`, `uploads/`, `state.json` |
| `listen` | `127.0.0.1:9000` | where S3 is served |
| `tls_cert`, `tls_key` | none | serve TLS directly; otherwise a TLS proxy in front terminates it. Current AWS SDKs send checksums as trailers only over TLS |
| `region` | `us-east-1` | the region clients sign for |
| `domain` | none | also serve `<bucket>.<domain>` |
| `chain` (`woc_key`, `woc_rate`), `settle` (`rpc_user`, `rpc_pass`, `arcade_key`), `headers` (`headers_token`) | `woc:main`, `arcade:main`, `woc:main`; the `test` ones when `mainnet` is false | the chain view (proofs, spends; `asset:<url>` for a node), the settlement leg (`arcade:`, `arc:`, `rpc:` or `tcp:`), the header source, as for a provider ([configuration.md](configuration.md#networks-and-endpoints)). `node`, the older key, is `chain: asset:<url>`. A regtest chain sets all three |
| `hosts` | required | overlay hosts asked and written to |
| `facade` | none | the plane: pieces and records are submitted to it once |
| `providers` | none | providers pieces and entries are unicast to (their submit route); a facade or at least one provider is required |
| `quorum` | 1 | hosts that must take an entry when there is no facade |
| `ca` | none | a PEM file of certificates trusted besides the system's, for hosts, providers and advertisers |
| `fetch_private` | false | fetch from advertised URLs at loopback, private or link-local addresses; off, such an advertisement is never fetched from |
| `identities` | required | the writer identities, by name |
| `access_keys` | required | `{"id", "secret" or "secret_file", "identity", "buckets"}`; `buckets` (S3 names) limits the key |

| `bounty` | none | the hold bounty every put asks for: `satoshis`, `t`, `k`, `retention_seconds`, `deadline_blocks`, `check_c`. It is one amount for every put, and a provider races only if an even share among `k` covers its price for the object's size and the retention (provider.md): set `satoshis` for the largest object you put |
| `hold_ahead` | 8 | mined hold outputs of the bounty each identity keeps ready |

| `piece_ahead` | `piece_tree` | the piece outputs kept ready ahead of the puts, across the current tree, the trees held for a switch and the trees being minted; more trees are minted in the background when fewer are left |
| `entry_ahead` | half of `entry_tree` | the same for entry trees. A writer is held to the entry outputs ready per block interval, so set this to the puts one block interval must absorb; the trees stay `entry_tree` outputs each, so each entry carrier stays small |
| `piece_workers` | 4 | piece carriers a put mints and sends at once, at most 32 |
| `race.off` | false | leave the race, settlement and reclaim to the command line |
| `race.window_seconds` | 3,600 | the race window from the entry (spec section 9.4) |
| `race.tick_seconds` | 10 | the pause between background passes over the races |
| `race.budget` | 0 | the most paid for one settlement challenge a provider prices; 0 takes free answers only |
| `race.no_publish` | false | do not publish failed challenges as outcome records |
| `fee` | 100 satoshis per 1000 bytes, floor 100, cap 100/1000 | the miner fee policy ([the fee block](configuration.md#the-fee-block)); `fee_sat_per_byte` and `fee_floor` are its older keys |
| `refuse_unmined` | false | `fund -beef` takes mined payments only |
| `accept_threshold_sats` | 25000000 | a settlement whose largest payout is at or below it is remitted once arcade says the network took it and the chain view shows its inputs spent by it alone, before it mines (race state `remitted`); above it, remitted once mined. Needs settle through arcade or ARC |
| `accept_payer_limit`, `accept_total_limit`, `accept_window_seconds`, `accept_watch_seconds` | one and ten thresholds, 3600, 0 | the rest of the acceptance rule, as for a provider ([provider.md](provider.md)) |
| `store_bytes` | 8 GiB | the local store's bound |

### Set up

```console
$ go build -o bstore ./cmd/bstore
$ ./bstore s3d init -config s3d.json
identity main 03...
$ ./bstore s3d address -config s3d.json -identity main
$ ./bstore s3d fund -config s3d.json -identity main -beef payment.beef   # or -txid <txid>
$ ./bstore s3d run -config s3d.json
```

1. `init` creates each identity's wallet and prints its key. Back up the
   data directory: the keys are what the bucket's owner names and what
   pays for writes.
2. Give the identity's key to the bucket's owner, who names it in the
   chain's `writers` (`bstore bucket new -writers`, or `bstore anchor
   -add-writer`, [usage.md](usage.md)). Until then the identity's writes
   are never anchored.
3. Pay the identity's fund address from your own wallet and import the
   payment: `fund -beef FILE` with the BEEF your wallet handed over (it
   need not have mined; `-refuse-unmined` takes mined payments only), or
   `fund -txid` once it has a block. A put spends one
   funding output per piece and one per entry, a funding tree's fee, and
   the bounty when one is configured. (`rescan -from` and `fund -blocks`
   are coinbase: only on a regtest chain you run, for development and
   tests.)
4. Run behind a TLS proxy, or with `tls_cert` and `tls_key`. `/healthz`
   answers `ok`.

Point a client at the gateway with path-style addressing, for example:

```console
$ aws --endpoint-url https://s3.example.com s3 cp ./photo.jpg s3://example-photos-hmqzvtkwrx/albums/photo.jpg
```

### Day to day

- The pending entries live in `pending.log` (appended, compacted when it
  grows), the tokens held in `state.json`. Each identity's state is two
  parts under its directory. `publisher.json` is what a put changes: the
  funding trees without their bytes, the hold outputs (one entry a hold
  transaction, a row an output: index, taken, the entry that names it),
  the buckets, sweeps, uploads and payments. It is written in batches: a
  put returns once the write that holds its change is synced, and the
  changes of the puts in flight together are one write; at 4,096 hold
  outputs ready it is under 30 KB. `txs/<txid>.json` is each transaction
  the state keeps (a hold transaction, a funding tree): its bytes, its
  proof once mined, and the BEEF a tree carries until then; written when
  the transaction is minted and once more when it mines, and removed once
  no record names it. A state an earlier release kept in `publisher.json`
  alone is read as it is and written in the two parts on the first save
  (the identity is then not for an earlier release). The races are their
  own files under `races/`.
- `/metrics` on `metrics_listen`: `bstore_s3d_requests_total{op,status}`,
  `bstore_s3d_bytes_in_total`, `bstore_s3d_bytes_out_total`,
  `bstore_s3d_part_bytes_total`, `bstore_s3d_entries_total`,
  `bstore_s3d_put_retries_total` (puts and copies answered from the entry
  an earlier send made or is still publishing), and the gauges `bstore_s3d_races_remitted_stale` (races
  remitted before mining whose proof the chain view has not served for an hour;
  alert on it above 0) and `bstore_s3d_race_remitted_oldest_seconds`. Two
  histograms say where a put's time goes:
  `bstore_publish_submit_seconds{target}` is each send of a carrier to the
  plane (the facade), a host or a provider, request to answer, and
  `bstore_publish_piece_seconds{stage}` is each piece carrier's `read` (the
  object out of the local store), `mint` (the carrier and its BEEF),
  `outbox` (its line written and synced) and `send` (every target answered).
- A bucket chain's walk in progress is kept under `walks/`, one file a
  chain, removed once the walk completes; a restart resumes from it.
- The log names every host whose answer did not verify, every advertiser
  that served wrong bytes, and every object not yet delivered.
- A stop (`SIGINT`, `SIGTERM`) finishes what it can; a crash loses
  nothing that was answered: the outbox and the funding records are
  synced before they are used, and the next start sends and settles
  what was in flight.
- The owner anchors on its own cadence (`bstore anchor`); until it does,
  only this gateway reads the writes it made.
- The gateway holds each identity's directory while it runs: a second
  process (a `bstore` command with `-home` at it) is refused until the
  gateway stops, and a gateway started while such a command runs waits for
  it, up to ten minutes, before it starts.

### Test it end to end

```console
$ make s3-e2e REFERENCE_HOST=/path/to/reference-host NODE=/path/to/node24
```

A reference overlay host loading the bstore module, over MySQL (Docker),
on a local test chain, with two providers, a test-only bucket owner, the
gateway over TLS, the AWS CLI and Terraform (or OpenTofu) when installed:

keys over two host pages with pagination, a delimiter and `start-after`;
`NoSuchKey` from a proof of absence; and Terraform's S3 backend writing its
